Local sandboxes record captured output to disk so you can read it later, even after the sandbox stops or crashes. Use `msb logs <name>` from the CLI or `logs()` from the SDK. For a running cloud sandbox, use `msb logs -f <name>` or the SDK's live log stream; bounded cloud history is not yet available.

## Read logs

```bash
msb logs devbox
msb logs devbox --tail 100
msb logs devbox -f
msb logs devbox --grep ERROR
msb logs devbox --json | jq 'select(.s == "stderr")'
```

The default output includes user-program `stdout`, `stderr`, and PTY output. Add system diagnostics when you need runtime or kernel logs:

```bash
msb logs devbox --source system
msb logs devbox --source all
```

## Read from the SDK

<CodeGroup>
```typescript TypeScript
const handle = await Sandbox.get("web");
const entries = await handle.logs();
```

```rust Rust
let handle = Sandbox::get("web").await?;
let entries = handle.logs(&LogOptions::default())?;
```

```python Python
handle = await Sandbox.get("web")
entries = await handle.logs()
```

```go Go
handle, err := m.GetSandbox(ctx, "web")
entries, err := handle.Logs(ctx, m.LogOptions{})
```
</CodeGroup>

Use log options to filter at read time:

<CodeGroup>
```typescript TypeScript
const recent = await handle.logs({
    tail: 50,
    sources: ["stdout", "stderr"],
});
```

```rust Rust
let recent = handle.logs(&LogOptions {
    tail: Some(50),
    sources: vec![LogSource::Stdout, LogSource::Stderr],
    ..Default::default()
})?;
```

```python Python
from microsandbox import LogReadSource

recent = await handle.logs(
    tail=50,
    sources=[LogReadSource.STDOUT, LogReadSource.STDERR],
)
```

```go Go
recent, err := handle.Logs(ctx, m.LogOptions{
    Tail: 50,
    Sources: []m.LogSource{m.LogSourceStdout, m.LogSourceStderr},
})
```
</CodeGroup>

## Sources

| Source | Meaning |
|--------|---------|
| `stdout` | Captured from a non-interactive session's stdout |
| `stderr` | Captured from a non-interactive session's stderr |
| `output` | Captured from a PTY session, where stdout and stderr are merged |
| `system` | Lifecycle markers plus runtime and kernel diagnostics |

Interactive sessions use a PTY, so stdout and stderr are merged before microsandbox receives them. Non-interactive `exec` calls keep the streams separate.

## Diagnostic flows

**Sandbox crashed**

```bash
msb ls
msb logs <name>
msb logs <name> --source system
```

**Sandbox will not start**

```bash
msb create --name nope ...
msb logs nope --source system
```

**Program produced no logs**

`msb create` only boots a sandbox. Run something with `msb run`, `msb exec`, or an SDK `exec` call to produce user-program output.

## On disk

Sandbox logs live under `<sandbox-dir>/logs/`:

| File | Contents |
|------|----------|
| `exec.log` | User-program output as JSON Lines |
| `runtime.log` | Sandbox runtime diagnostics |
| `kernel.log` | Guest kernel and agent console output |
| `boot-error.json` | Structured startup failure details, when boot fails early |

### Rotation and archives

`exec.log` and `runtime.log` rotate at 10 MiB into `<file>.1` through `<file>.4`; `.1` is the newest. When `.4` would be overwritten, it is moved to an archive named `<file>.<UTC timestamp>`, for example `runtime.log.20261018T143005Z`, with a `-<n>` suffix when two archives share a second. A background thread compresses each archive to `<file>.<UTC timestamp>.gz` and removes the uncompressed file once the compressed file is written. If compression fails, the uncompressed archive stays and a warning is written to `runtime.log`.

`kernel.log` is replaced on every boot. Before a restart, the previous `kernel.log` is archived and compressed the same way.

`msb logs` and the SDK log readers read the live files and the `.1` to `.4` chain only. Archives are for operators and tools that need older output. microsandbox never deletes archives; the embedder or operator is responsible for deleting them. Removing a sandbox deletes its sandbox directory, including the default `logs/` directory and its archives.

### Choose the log directory

An embedder can keep logs outside the sandbox directory so they outlive the sandbox. Pass a log directory at creation; microsandbox creates it if needed and makes `<sandbox-dir>/logs` a symlink to it. `msb logs`, the SDK log readers and later starts use the directory through that symlink. Removing the sandbox removes only the symlink, so the files and their cleanup stay with the caller. Use a separate directory for each sandbox. The option is available for local sandboxes on Linux and macOS.

<CodeGroup>
```rust Rust
let sandbox = Sandbox::builder("worker")
    .image("alpine")
    .log_dir("/var/lib/myapp/logs/worker")
    .create()
    .await?;
```

```go Go
sb, err := m.CreateSandbox(ctx, "worker",
    m.WithImage("alpine"),
    m.WithLogDir("/var/lib/myapp/logs/worker"),
)
```
</CodeGroup>
